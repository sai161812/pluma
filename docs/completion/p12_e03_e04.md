# P12 E-03/E-04: duplicate-label and stale-reference acceptance (E63)

## Outcome

The second bounded P12 task passes. A registered UIA inspection exposed two real `Submit` buttons with identical labels on an owned Win32 fixture. A subsequent registered click request using either returned element reference was refused at parent grounding with `UI_AMBIGUOUS_TARGET`, before action-worker admission. Independent UIA reads confirmed both buttons remained enabled.

A separate registered click request was grounded in a fresh snapshot from the fixture's primary HWND. The task context then changed to the fixture's second, independently owned HWND. The action returned `WINDOW_MISMATCH` before constructing the UIA action adapter. Independent reads confirmed the primary Submit button and both buttons in the second window remained enabled.

## Implementation

- `pluma/tools/registry.py` now counts exact, case-insensitive labels from the selected perception source in the resolved task snapshot. `click_element` and `type_into_element` refuse duplicate labels before starting a worker; a matching OCR and UIA label does not create a false duplicate across sources.
- `tests/fixtures/uia_semantic_target.py` now owns two non-activating Win32 windows: one with a unique Submit button and a second with two same-label Submit buttons. The fixture process remains a single owned process and exits only after both fixture windows close.
- `tests/windows/test_p12_uia_semantic_controls.py` exercises E-03 and E-04 through the registered inspect/click tools, real Win32 identity reads and the Windows UIA provider. It verifies both refusals precede any UIA action and reads the controls back after each refusal.
- `tests/unit/test_phase13_5_regression.py` covers duplicate-label rejection at the registry boundary; the OCR substring ambiguity regression remains included in the focused suite.

The active-window change is selected through a test context that returns fresh native metadata for either exact owned HWND. The current session does not provide a foreground/focus acceptance environment, so the tests do not activate or inspect any pre-existing user window. This evidence proves the production stale-HWND guard and no-action result; it does not claim a physical foreground transition.
