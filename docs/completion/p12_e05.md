# P12 E-05: refresh window geometry and DPI before OCR coordinate fallback (E64)

## Outcome

E-05 passes. `click_ocr_text` now refreshes the target's active-window identity, process creation time, geometry and DPI after OCR and before translating an OCR match into desktop coordinates. It refuses the action if the HWND/PID/process creation identity changed, the window moved or resized, geometry is unavailable, or DPI differs from the capture-time scale. The refreshed rectangle is used for coordinate translation only after the checks pass. A supplied snapshot still receives its existing TTL and identity validation before input.

The refusal is deliberate: OCR coordinates describe the captured pixels. If the target moves, resizes or changes DPI while OCR runs, PLUMA must capture and recognize again before trying a coordinate action. No input occurs on this stale-coordinate path.

## Implementation and acceptance

- `pluma/tools/ui.py` captures the target's initial PID, process creation time, valid rectangle and DPI, then refreshes them after OCR. Geometry must match the capture rectangle exactly; a DPI scale difference greater than 0.05 is refused. Coordinates are derived from the fresh rectangle only after process identity, geometry, DPI and optional snapshot checks.
- `tests/unit/test_ocr_grounding_integration.py` covers a moved rectangle, DPI drift, PID change and recycled PID without a supplied snapshot; every case asserts that `InputAdapter.mouse_click` is never called.
- `tests/windows/test_p12_uia_semantic_controls.py` exercises the registered `click_ocr_text` tool against an owned native Win32 fixture. Its OCR stub moves that fixture while recognition is in progress; fresh native geometry detects the move and the test confirms no input dispatch. The fixture is the only window moved.

The native acceptance changes only the owned fixture's window position. The DPI-change path is deterministic unit coverage; the system display scaling was not changed. No pre-existing user window was activated or modified.
