# PLUMA Agent Contract

This file is an execution contract for any coding agent working in this
repository. `PLUMA_MASTER_SPEC.md` is the authoritative product and
engineering specification. Read it completely before changing code.

## Authority and scope

- Build **PLUMA**, never FEATHER or another renamed product.
- Treat `PLUMA_MASTER_SPEC.md` as immutable source material. Do not silently
  relax, remove, rename or reinterpret a locked requirement.
- If a requirement is ambiguous, stop and ask the project owner. Do not fill
  the gap with a generic agent pattern.
- Do not invent the visual design. Implement only functional UI contracts until
  the owner supplies the visual direction.
- Do not add features because they look “AI”, “agentic” or impressive.

## Non-negotiable runtime laws

1. The installed resident process must be lightweight. LLM, STT, OCR, screen
   capture loops and GPU inference are not loaded merely because PLUMA starts.
2. Voice is mandatory and enters the same request, routing, policy, tool,
   verification and ledger pipeline as text.
3. Natural language is never an execution API. Every real action is a
   registered, typed `ToolSpec`.
4. Prefer native/application APIs, then controlled PowerShell/CLI, then UIA,
   then stable keyboard/input, then targeted OCR-grounded input, and raw
   coordinates only as a last resort.
5. Every state-changing action has a postcondition and must read it back before
   reporting success.
6. Every reversible action captures the minimum safe pre-state needed for an
   evidence-based undo record.
7. Every command is one `TaskCapsule` owned by one `TaskSupervisor` and one
   cancellation tree. No detached task branches or untracked subprocesses.
8. STOP has priority over planner inference, STT, OCR, UI waits, shell calls and
   tool workers.
9. The STOP latch is set first. Once set, no new tool call, replan or branch may
   begin for that task.
10. Force termination is restricted to PLUMA-owned workers/process trees unless
    the user explicitly requested termination of another process.
11. Speed improvements may remove wasted work, never required policy,
    verification, cleanup or safety checks.
12. Activity history is factual system data generated by deterministic executor
    templates, never LLM-written narrative or hidden reasoning.

## Safety and privacy boundaries

- No unrestricted shell or administrator access is exposed to the planner.
- Validate tool names and arguments against the registry before policy checks.
- Use bounded timeouts for every external call and worker.
- Register every subprocess with task ID, PID, creation time, command class and
  ownership; place task descendants in a Windows Job Object where applicable.
- Never touch pre-existing user windows, tabs, files or processes during STOP
  cleanup unless the explicit operation requested it.
- Mark irreversible external commits as non-undoable; never promise impossible
  rollback.
- Redact passwords, tokens, private clipboard values, raw audio and sensitive
  arguments from stored logs.
- Do not persist screenshots or raw microphone audio by default.
- Treat UIA/OCR screen references as short-lived. Re-check active-window
  identity and geometry before coordinate-based interaction.

## Architectural boundaries

Code outside adapters and perception workers must not depend directly on:

- pywinauto classes;
- OCR-library objects;
- PowerShell implementation details;
- a particular local model, model file or inference server.

Use interfaces/adapters so the technology can be replaced without rewriting the
orchestrator, policy engine, verifier, rollback engine or Activity Ledger.

The planner may propose only registered `ToolCall` objects. It may not import or
invoke pywinauto, Win32, PowerShell, OCR, keyboard or shell libraries directly.

## Required agent workflow

For every task:

1. Read the relevant sections of `PLUMA_MASTER_SPEC.md`, this file and the
   current phase in `PLUMA_BUILD_PLAN.md`.
2. Inspect the existing repository and tests before editing.
3. State the exact files that will change and the acceptance tests that will
   prove the change.
4. Implement only the requested phase or bounded bug fix.
5. Run focused tests, then the relevant regression suite.
6. Inspect `git diff` for accidental scope, secrets, fake success paths and
   generated UI copy.
7. Report changed files, commands run, results, known limitations and the next
   safe step.

Do not continue automatically into another phase. Do not rewrite working code
just to change its style. Do not use destructive commands such as repository
resets or broad recursive deletes.

## Required completion evidence

A phase is incomplete until the corresponding checks in
`PLUMA_ACCEPTANCE_TESTS.md` pass or a concrete, recorded limitation is approved
by the owner. A claim of “done” must include test output and must not rely only
on a successful function return or a visual impression.
